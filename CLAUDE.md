## Database Rules (strict — always follow)

Neon is shared/pre-provisioned production data, not throwaway. **Never apply a migration in one step.** Required workflow for any schema change:
1. Inspect current `src/db/schema.ts` and live Neon schema (read-only Neon MCP) first.
2. Write ONE additive-only SQL migration (no DROP/TRUNCATE/DELETE/ALTER-type-change/table recreation).
3. Show the exact SQL + confirm it's additive. Stop — do not apply yet.
4. If using a runner script, show its complete contents too (must read the exact reviewed SQL file, no destructive statements, secrets via `process.env["KEY"]` bracket notation never printed, wrapped in `BEGIN`/`COMMIT` with `ROLLBACK` on failure).
5. Only after explicit approval of both, execute.
6. Re-query live DB afterward to verify (don't trust script exit code alone) — confirm exact expected tables/columns exist and nothing unrelated changed.
7. Report and stop — don't chain into more migrations/wiring/commits unless separately asked.

**Why drizzle-kit push/generate don't work here:** base tables (`user`, `session`, `account`, `verification`, `audit_log`) were provisioned outside this repo pre-Drizzle (leftover `_prisma_migrations` table proves earlier Prisma provisioning, no Prisma files remain). No `drizzle/` migration history exists, so `drizzle-kit generate` would try to recreate everything; `drizzle-kit push` fails outright (no TTY in this shell). Instead: hand-write additive SQL, execute via a throwaway Node script using `pg` + `DATABASE_URL`, wrapped in BEGIN/COMMIT/ROLLBACK. The Neon MCP server available here is **read-only** — schema inspection only, never write SQL through it.

## AI Architecture (`src/lib/ai/`)

## Cloudflare Workers Runtime (ASCEND A1 — runtime foundation verification, 2026-08-18)

Deploy target is confirmed **Cloudflare Workers**, not Node: `@lovable.dev/vite-tanstack-config`'s bundled `nitro` plugin defaults to nitro's `cloudflare-module` preset (`vite.config.ts` comment already documented this; confirmed concretely via the generated `.output/server/wrangler.json` — `nodejs_compat` flag, `ASSETS` binding, `no_bundle: true` ESM output, `main: index.mjs`). No `wrangler.toml`/`.jsonc` is checked into the repo; it's generated fresh by `npm run build`.

**DB driver verdict: `pg` is PRODUCTION-SAFE here — do not migrate to `@neondatabase/serverless`.** Verified from the actual bundled output, not inferred:
- `pg` (via its bundled `pg-cloudflare` runtime-detection layer) auto-switches `node:net`/`node:tls` for the native `cloudflare:sockets` `connect()` API + `startTls()` when running under Workers — confirmed present in `.output/server/_libs/drizzle-orm.mjs` (`CloudflareSocket` class, `await import("cloudflare:sockets")`).
- `DATABASE_URL` already points at Neon's **pooled** (`-pooler`) PgBouncer endpoint, so no Hyperdrive binding is needed — Neon's own pooler already does the connection-multiplexing job Hyperdrive would otherwise provide. No Hyperdrive config exists anywhere in the repo, and none is required.
- `env.DATABASE_URL` correctly reaches `process.env` at runtime: nitro's cloudflare-module handler sets `globalThis.__env__ = env` per-request (`node_modules/nitro/dist/presets/cloudflare/runtime/_module-handler.mjs`), and unenv's `process.env` polyfill reads from `__env__`. Critically, `src/db/index.ts`'s `new Pool({ connectionString: process.env["DATABASE_URL"] })` only ever evaluates inside the **lazily-imported** SSR chunk (`defineLazyEventHandler(() => import("./_chunks/ssr-renderer.mjs"))`), which is first imported *inside* the per-request `fetch()` handler, after `__env__` is already set — never at Worker module-load/top-level time. So this is correctly wired, not a hidden bug.
- Real DB smoke test passed (temporary, dev-only Node script using the exact same `pg` + pooled `DATABASE_URL` the app uses, deleted immediately after): `SELECT 1` connectivity, a real `SELECT count(*) FROM "user"`, a transaction-wrapped `INSERT` + read-back + `ROLLBACK` against the FK-free `verification` table (confirmed zero persistence via a follow-up count), and a controlled-failure case (query against a nonexistent table correctly threw `42P01`, not swallowed).

**ACTUAL blocker found — unrelated to `pg`/the database — the Worker does not currently boot at all under the real Cloudflare Workers runtime.** Running the production build through `wrangler dev --local` (real `workerd`, not just Vite's dev SSR) fails immediately: `Uncaught SyntaxError: Export 'ssr_exports' is not defined in module` at `.output/server/_ssr/ssr.mjs`, followed by `The Workers runtime failed to start.` The identifier `ssr_exports` appears nowhere else in the entire `.output/server` tree — a dangling/broken export binding generated by nitro's (`nitro@3.0.260603-beta`, explicitly beta) `cloudflare-module` bundling of the SSR chunk. **Reproduced identically on the clean, last-committed tree** (`b073328`, verified via a reversible `git stash`/rebuild/`git stash pop` round-trip) — so this is pre-existing, not caused by any currently-uncommitted work, and simply hasn't been caught before because every prior phase's verification (see Build Phase History below) only ever ran `npm run build` + Vite dev server + browser, never the actual Workers runtime. Not fixed in this phase (root-causing/fixing a beta bundler's tree-shaking output is well beyond a "smallest safe config change" and needs its own dedicated investigation — likely a nitro version bisect or upstream report).

### ASCEND A2-B / A2-C — DB connectivity through the real deployed Worker (COMPLETE, verified, 2026-08-18)

Resolves A2's "DB write through the Worker: UNVERIFIED" item above — that text is now superseded, kept for history. Two rounds:

**A2-B (Hyperdrive wiring):** Added Cloudflare Hyperdrive as an alternate DB connection path. Created via `wrangler hyperdrive create creatoros-neon-db --connection-string=... --binding=HYPERDRIVE`, pointed at the existing Neon database — no new database, no schema change. Wired via a new project-root `wrangler.jsonc`: nitro looks for a `wrangler.json`/`.jsonc`/`.toml` via `findNearestFile` from `rootDir` and merges it into the generated `.output/server/wrangler.json` at build time (confirmed in `node_modules/nitro/dist/_presets.mjs`'s `writeWranglerConfig`) — this is the correct, supported way to add Cloudflare bindings without hand-editing generated output or needing `@lovable.dev/vite-tanstack-config`'s narrow `nitro` option (which doesn't expose a `wrangler` passthrough). `src/db/index.ts` now prefers `process.env["HYPERDRIVE"]?.connectionString`, falling back to `process.env["DATABASE_URL"]` — same `Pool`/`drizzle()` call, local dev unaffected.

**A2-C (the actual root cause):** deploying with Hyperdrive still failed identically (`proxy request failed, cannot connect to the specified address`). Root-caused via a temporary diagnostic route deployed to production (removed once done) plus static analysis of the built bundle — two independent, compounding gaps, **neither related to `pg`/`cloudflare:sockets`'s ability to reach a public host**, which corrects A1/A2's original conclusion above:
1. Code using the bare `import ... from "node:process"` specifier (e.g. `src/db/index.ts`'s compiled chunk) resolves to `workerd`'s own **native** process implementation under the `nodejs_compat` flag alone — its `.env` stays empty by design unless the separate `nodejs_compat_populate_process_env` compatibility flag is also set. This is why `DATABASE_URL` always read as `undefined`, and `pg` silently fell back to its own default `localhost:5432` target, which then failed under `cloudflare:sockets` with the same generic error every time — a red herring that looked exactly like a "can't reach external hosts" problem but wasn't.
2. Independently: nitro's outer Cloudflare handler receives `env` correctly and does set `globalThis.__env__ = env`, but its internal dispatch (`h3App.fetch(req)`) only ever passes the bare request onward — TanStack Start's own server-entry is invoked with `env` always `undefined`. The only place the real bindings survive that entire chain is `request.runtime.cloudflare.env`, attached by nitro's own `augmentReq()` at the true entry point.

Fix: added `"nodejs_compat_populate_process_env"` to `compatibility_flags` in `wrangler.jsonc` (the actual fix — covers plain-string bindings: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`). Added `restoreCloudflareEnv()` in `src/server.ts`, reading `request.runtime.cloudflare.env` and re-populating `globalThis.__env__`, threaded through to TanStack's handler — belt-and-suspenders, and also the only route to object-typed bindings like Hyperdrive (the flag doesn't cover those).

**Verified live** on a clean deploy (Version `4fde4c94-a4a6-49e0-ad9f-92fd0ee1c327`, all diagnostic code removed): real DB query succeeded; real signup (200, user + session created, confirmed in Neon); authenticated session read (200); logout (200, session row deleted — confirmed via Neon, 0 remaining); duplicate-signup controlled failure (422, clean error, zero extra rows); SSR routes (`/`, `/login`, `/privacy`) all 200. `npx tsc --noEmit`: 0 errors. `npm run build`: clean.

Side finding: the successful query went through the `DATABASE_URL` fallback, not Hyperdrive (the compat flag only populates plain-string bindings) — Hyperdrive isn't load-bearing for the fix, though it remains deployed as an optional future connection-pooling layer.

**Known non-blocking issue:** two Cloudflare error-1101 ("Worker hung") responses occurred during testing immediately after fresh deploys; both resolved cleanly on immediate retry and didn't recur — consistent with cold-start jitter, not reproduced as a real bug.
